# RFC: Support Chat A/B Test

**Audience:** BUCKS developers, product reviewers, and support agents.  
**Status:** Draft; no experiment code implemented.  
**Author:** AI-assisted draft from developer requirements.  
**Reviewers:** Product, engineering, and support operations.  
**Type:** #experiment-rfc

## 1. Goal

**Start meaningful support conversations.** Compare two ways of offering help in the BUCKS admin. Support agents decide whether conversations were meaningful during weekly reviews, using 7-day and 14-day observation windows.

Chat openings, automatic messages, and trigger counts are not conversions by themselves. No merchant setting or storefront/widget change is proposed.

## 2. A and B Behavior

| | A: Agent greeting | B: Automatic visitor message |
| --- | --- | --- |
| Chat starts | App displays the existing agent-style greeting and opens chat | App automatically sends the feature message as the visitor and opens chat |
| When to request a Crisp trigger count | First genuine merchant reply after the greeting, in the same tab session | Confirmed automatic message send |
| What must not count | Showing the greeting, historical messages, or app-generated messages | Merely queueing a send command, or later replies as additional B send counts |
| Conversion | Agent-reviewed meaningful conversation | Same review rule as A |

The app owns message display/sending. Neither variant uses the existing `_message` greeting events during the test; disable or isolate their old automations for experiment traffic to avoid duplicate messages and counting A's greeting. Manual support remains independent.

**B message copy:**

| Feature | Message |
| --- | --- |
| App embed | BUCKS app embed isn’t activating. Can you help? |
| Position | Trying to figure out how to position the currency converter on the store! |
| Cart | Yay! Cart Notification is now enabled! 🎉 |

Confirm the corrected cart wording before launch. Support must know B's message was generated by the app, not deliberately typed by the merchant.

## 3. Assignment and Existing Limits

- Assign one stable A/B variant per shop across Home, Settings, Advanced, and later visits, including direct page loads.
- Use server-side hashing of normalized authenticated shop domain plus experiment key `support_chat_v1`. Expect approximately 50/50, not an exact split. Keep the algorithm/key fixed during the test.
- Reuse the concept in `docs/AB_TESTING_IMPLEMENTATION.md`; its referenced `assignVariant.js` and `onboarding_variant` implementation were not found in the current code. Keep this experiment independent of onboarding.
- No assignment database table or Prisma schema change is proposed. Do not import server hashing code into browser/widget bundles. If assignment is unavailable, use non-experiment A behavior and exclude the attempt from experiment reporting.
- Keep existing eligibility: embed after three failed manual dashboard checks within two minutes; position/cart after three seconds; one proactive attempt per tab; position/cart once per shop installation, becoming eligible again on reinstall.
- Do not reset existing consumed records for this test. Preserve cancellation, claim retries, and impersonation exclusion. Later eligible features remain context-only and do not replace the first feature's pending reply context.

## 4. Six Crisp Triggers

Each event below means either **A received a reply** or **B sent its automatic message**. It is not a conversion verdict. Configure six separate saved triggers using **On user event**:

| Feature | Variant | Trigger identifier | Event name |
| --- | --- | --- | --- |
| Embed | A | `bucks-support-a-embed-reply` | `bucks_support_a_embed_reply` |
| Position | A | `bucks-support-a-position-reply` | `bucks_support_a_position_reply` |
| Cart | A | `bucks-support-a-cart-reply` | `bucks_support_a_cart_reply` |
| Embed | B | `bucks-support-b-embed-sent` | `bucks_support_b_embed_sent` |
| Position | B | `bucks-support-b-position-sent` | `bucks_support_b_position_sent` |
| Cart | B | `bucks-support-b-cart-sent` | `bucks_support_b_cart_sent` |

Send the corresponding profile event once per activation. An **activation** means one eligible attempt to start the help experience, identified by a unique `activation_id`.

**Not yet verified:** whether a saved Crisp trigger can count without showing another message or performing another visible action. Confirm this before implementation. Do not fabricate `trigger:fired` or add unwanted messages to force a count. Crisp can also suppress triggers already fired for a visitor, so native counts may be lower than actual reply/send events.

### Detecting A's same-tab reply

1. Before showing the greeting, register one shared Crisp `message:sent` listener.
2. Store shop/installation, experiment, variant, feature, activation ID/time, and reply-counted status in `sessionStorage`.
3. On the first genuine merchant send after A starts, emit its feature-specific reply event and mark it counted. Exclude agent messages, profile events, historical messages, and app-generated sends.
4. Preserve context across same-tab navigation/reload. Closing the tab ends browser attribution; other-device or later-session replies are excluded from this automatic count, but can still be reviewed manually.

Verify whether Crisp callbacks synchronize across tabs and how automatic sends can be correlated. Duplicated tabs may inherit session storage. Do not claim exact same-tab detection until tested, and do not identify automatic sends by text equality or "ignore the next message" alone. Avoid duplicate listeners or removing another feature's listener.

For B, verify a reliable send-confirmation callback. If only submission is observable, revise the event/report wording before launch rather than claiming the message was sent.

## 5. PostHog and Crisp Context

### PostHog

Record `bucks_support_activation` once per eligible help attempt. Assignment alone is not activation; activation is not proof the message displayed.

Include `experiment`, `variant`, `myshopify_domain`, `feature`, `activation_id`, `source`, `message_origin`, and the event timestamp. Attach the Crisp session/conversation reference when available so agents can locate the conversation. Set experiment/variant explicitly on events; hashing does not automatically create a PostHog feature-flag experiment.

Preserve existing feature context/PostHog events. Keep each activation in event history; do not send chat text, credentials, or unnecessary personal data to analytics.

### Crisp segments and custom data

After readiness, automatically add one segment through `session:segments`:

- A: `bucks-support-v1-a`
- B: `bucks-support-v1-b`

These labels group participating conversations for review, not conversions. Add them on activation and preserve unrelated segments. Verify available inbox filters in the workspace; flag conversations with both A/B labels for review.

Set these fields through `session:data`:

| Key | Value |
| --- | --- |
| `bucks_support_experiment` | `support_chat_v1` |
| `bucks_support_variant` | `A` or `B` |
| `bucks_support_feature` | `embed`, `position`, or `cart` |
| `bucks_support_activation_id` | Unique activation ID |
| `bucks_support_activated_at` | ISO timestamp |
| `bucks_support_message_origin` | `agent_greeting` or `automated_visitor` |

Custom data describes the latest activation; PostHog/profile events preserve history. Do not configure message automations on these fields, segments, or original context events. Only the six reply/send events should activate the new counting triggers.

## 6. Weekly Agent Review and A/B Result

Use the same definition for A and B: **genuine merchant participation plus a substantive support exchange relevant to the help context**. Automatic messages alone do not qualify. Product/support must approve this review rule before launch.

1. Get unique activated shops from PostHog, grouped by variant and enrollment week.
2. Review each group after a full **7 days**, then again after **14 days**. The 14-day cumulative result includes the first week; newly enrolled shops must wait for their full window.
3. Open matching Crisp conversations using their references and experiment labels. Include shops with no reply/no conversation in the denominator; do not review only visible inbox conversations. Review even if a browser reply event is missing.
4. Record experiment, variant, shop, feature, activation ID/time, conversation reference, reviewer, window, evidence note, and verdict: `meaningful`, `not_meaningful`, or `unclear`. Resolve unclear cases or report them separately.
5. Compare, separately for A and B:

   **Conversion rate = unique activated shops with a confirmed meaningful conversation / all unique activated shops.**

Deduplicate repeated activations by shop for the overall result; report feature breakdowns separately. A reply counts and B automatic-send counts are supporting information, not equivalent conversions. Also review duplicate messages, delivery failures, and support workload.

## 7. Implementation and Validation

| Area | Work |
| --- | --- |
| `pages/index.jsx`, `pages/settings/index.jsx`, `pages/advanced/index.jsx` | Server-assigned variant on every entry path |
| `utils/extras/chatTriggers.js` | A/B delivery, activation IDs, existing eligibility/claims |
| `components/hooks/useChatTriggers.js`, `utils/extras/crispChat.js` | Ready-runtime delivery, shared reply listener, tab attribution |
| `utils/extras/crispProfileEvent.js`, `utils/registerPostHogEvent.js` | Events, experiment context, non-blocking reporting |
| `pages/api/v1/user/chatTriggers.js` | Retain installation consumption and completion semantics |
| Sidekick references and tests | Update explanations and source citations with implemented behavior |

Analytics/tagging failure must not block merchant actions. Never automatically resend an ambiguously sent visitor message; completion retries must not replay delivery or tracking. Do not clear Crisp identity/history or installation claims to force balanced counts.

**Order:** verify Crisp capabilities first; implement assignment/delivery/tracking; validate all six cases with test shops; then enable through an internal rollout control. Disabling the experiment restores the pre-experiment delivery path without resetting claims or reassigning shops.

**Tests:** stable assignment across pages; A greeting does not request a count; first A reply counts once; B sends/counts once; no duplicate greeting in B; automatic sends are not human replies; correct shop/feature attribution; navigation/reload/cross-tab behavior; readiness/analytics failures; concurrent actions; existing timing, claims, and impersonation protection. Manually verify profile fields, PostHog properties, native counts, and agent review workflow.

### Decisions required before launch

- **Engineering/Crisp:** Can silent counting triggers work, and can send confirmation and same-tab human replies be identified reliably? If not, revise the design instead of promising those counts.
- **Product/support:** Approve the conversation-review rule, B wording, and automatic visitor-message behavior.
- **Product/analytics:** Choose baseline, minimum useful improvement, sample size, duration, and acceptable support workload. Do not copy onboarding example numbers or stop on an early apparent winner.
